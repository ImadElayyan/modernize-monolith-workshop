Carry out the reviewed Module 2B plan in checkpoints. A successful agent message is not the same as a working application.

1. Finish the framework upgrade

  1. Let Copilot apply the approved framework/package changes in your isolated repository.
  2. Inspect the resulting projects. Confirm the intended application targets net10.0 and unsupported references were handled.
  3. Build the upgraded solution in Visual Studio. Resolve the actual compiler errors before progressing.
  4. Review git diff and commit a working checkpoint. Copilot may already have made commits; use git log -5 --oneline to understand the current state.

Once the solution is SDK-style, CLI build commands are also available. From the folder containing the generated solution, run:

dotnet restore
dotnet build

If multiple solution files remain, specify the actual upgraded solution filename. Do not assume the agent preserved the original name. Run commands separately and stop on failure.

2. Move the database to SQLite

Continue the reviewed plan: migrate the sample data layer to SQLite.
First inspect what the framework upgrade already changed.
Use compatible EF Core packages and a local SQLite connection.
Preserve the sample schema, seeded products and store information.
Do not store credentials in code.
Explain the database initialization strategy and how to verify persistence.
Build and show the result before moving on.

Review the provider registration, connection configuration, seed logic and data access. Do not accept a configuration-only change if the pages still cannot load their data.

When EF migrations are actually needed

Inspect the generated code first: it may use migrations or EnsureCreated. Do not mix the two approaches blindly. If the plan uses migrations, confirm the EF CLI and design package match the project's EF Core version, inspect existing migrations, and choose the correct target/startup projects.

Only for a single-project app using migrations, from that project directory, with no existing initial migration, these commands may apply:

dotnet ef migrations add InitialCreate
dotnet ef database update

If the tool, DbContext or startup project cannot be found, resolve that specific error rather than repeatedly creating migrations.

3. Complete the Blazor conversion

Continue the reviewed plan: convert the remaining MVC UI to Blazor.
Inspect any Blazor work already completed and avoid duplicating it.
Preserve product and store-information behavior, navigation and images.
Use a coherent hosting model, routing and layout.
Remove obsolete files only after their replacement works.
Build, run and report which pages you verified.

Run the modernized web project using Visual Studio's startup profile. Check the URL reported by the application; do not assume the legacy IIS Express URL is still valid.

4. Verify the application yourself

Build succeeds, but the app is incomplete

The upstream guide explicitly notes incomplete frontend migration, missing assets and data-loading problems. Capture the exact failing route, log or compiler error and ask for a targeted fix. Do not mark the upgrade complete solely because the agent reports success.

This check failed: [describe the exact behavior].
Here is the relevant error or log: [paste non-sensitive details].
Compare the implementation with our agreed migration plan.
Explain the root cause, propose a focused fix, then rerun the failing check.
Do not remove functionality or suppress errors to make the check pass.
Lab 2 complete when

The .NET 10 application runs with SQLite and the intended Blazor UI, and you have a reviewed working checkpoint. Record any unfinished upgrade work and continue it afterward rather than marking it complete.
